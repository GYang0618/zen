# ADR-002：租户模型 — 单租户交付，tenantId 全链路就绪

- **状态**：已采纳  
- **日期**：2026-07-22  
- **决策者**：平台架构（Zen）  
- **相关**：[领域与安全](../architecture/domain-and-security.md) · [功能清单 TENANT-*](../product/feature-catalog.md) · [roadmap Phase 5](../implementation/roadmap.md)

## 背景

后台平台常见三条路径：

1. **纯单租户**：模型无 `tenantId`，企业内部系统最快  
2. **完整多租户**：一期交付租户生命周期、套餐、隔离与运营后台  
3. **Tenant-ready**：产品按单租户使用，但数据与上下文从第一天携带 `tenantId`

Zen 目标包含未来 SaaS / 多组织扩展可能，但第一版商务与交付范围是**单租户可用的优秀平台基础**。

## 决策

**采用 Tenant-ready：单租户交付 + 全链路 `tenantId` 就绪。**

具体约束：

1. 引入 `Tenant` 实体；种子默认租户（如 `default`）。  
2. 租户相关表、唯一约束、索引均包含 `tenantId`（平台级全局表除外并明文列出）。  
3. 请求级 **Tenant Context** 必填；Repository 默认带租户过滤。  
4. 缓存键、文件路径、任务载荷、事件 Envelope、审计日志均含 `tenantId`。  
5. **第一阶段不交付**：租户开通/冻结 UI、套餐配额、跨租户超管切换（可留接口桩）。  
6. 角色与权限绑定在租户内（Membership ↔ Role），避免未来改造时权限泄漏。

## 理由

| 因素 | 说明 |
|------|------|
| 返工成本 | 后期加 `tenantId` 往往涉及全表迁移、唯一约束重建、缓存与文件路径改造 |
| 交付范围 | 避免一期陷入租户运营与计费，聚焦内核与插件系统 |
| 安全 | 从第一天强制「查询必带租户」习惯，降低漏过滤风险 |
| 扩展 | 多租户启用时主要补生命周期与路由解析，而非翻领域模型 |

## 后果

### 正面

- 领域模型面向未来，避免推倒重来  
- 开发期即可用集成测试断言「跨租户不可见」  
- 与插件安装表、事件、任务设计一致  

### 负面 / 风险

- 短期模型比纯单租户略重（多一列与上下文）  
- 若永远不做多租户，存在少量「过度设计」——可接受为平台级保险  
- 简化实现时易误把 `tenantId` 写成可选——**禁止**；默认租户也必须显式写入  

### 不做什么（一期）

- 租户注册、计费、配额仪表盘  
- 域名 / Header 解析多租户路由（可预留扩展点文档）  
- 跨租户数据共享策略引擎  

## 全链路就绪检查表

| 层 | 要求 |
|----|------|
| DB | `@@unique([tenantId, code])` 等；禁止仅用全局 unique 表达租户内唯一 |
| API | Context 中间件；禁止无租户裸查（特殊运维 API 需显式审计） |
| Cache | key 前缀含 `tenantId` |
| Files | 对象键 `/tenants/{tenantId}/...` |
| Events | Envelope.tenantId 必填 |
| Jobs | 载荷含 tenantId；执行时恢复 Context |
| Audit | 每条审计含 tenantId |
| Plugins | `plugin_installations` 按租户；配置按租户 |

## 升级触发条件（完整多租户）

1. 明确多客户数据隔离的产品/商务需求  
2. 租户解析策略确定（子域 / Header / Token claim）  
3. 完成配额、冻结、备份隔离 runbook  
4. 安全测评覆盖跨租户 IDOR  

届时新增 ADR 描述租户路由与运营模型，本 ADR 保持「就绪策略」有效，或标记「部分被扩展」。

## 备选方案（未采纳）

| 方案 | 未采纳原因 |
|------|------------|
| 纯单租户无 tenantId | 未来 SaaS 改造成本过高 |
| 一期完整多租户 | 范围膨胀，拖慢平台内核与插件系统 |
| 仅部分表加 tenantId | 半隔离状态最危险，易漏 |
