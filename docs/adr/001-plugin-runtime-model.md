# ADR-001：插件运行模型 — 编译期优先，运行时预留

- **状态**：已采纳  
- **日期**：2026-07-22  
- **决策者**：平台架构（Zen）  
- **相关**：[插件系统](../architecture/plugin-system.md) · [仓库结构](../architecture/repository-structure.md) · [roadmap Phase 5](../implementation/roadmap.md)

## 背景

Zen 需要「平台基础 + 插件扩展业务」。可选模型包括：

1. **编译期 Monorepo 插件**：`plugins/*` 与平台同仓构建、同版本发布  
2. **运行时热插拔**：独立包/zip，进程内动态加载或 Module Federation  
3. **混合**：核心编译期 + 少量集成类运行时安装  

同时存在信任模型选择：仅第一方 vs 允许不可信第三方。

## 决策

**采用方案：第一方编译期插件，并预留运行时扩展面（Manifest / SDK / 贡献点稳定化）。**

具体约束：

- 插件与平台使用同一 Turborepo / pnpm workspace 发布。
- 不提供第三方代码沙箱、签名市场或真正热卸载 JS 模块（第一阶段）。
- 启停通过 `plugin_installations` + Registry 过滤实现「逻辑停用」，不是从磁盘热加载。
- Schema / Migration **集中**在 `apps/api/prisma`；卸载**不**自动回滚表结构。

## 理由

| 因素 | 说明 |
|------|------|
| 交付速度 | 复用现有 Nest Module、TanStack 路由、OpenAPI→Agent 链路，阻力最小 |
| 安全 | 第一方可信 + Code Review/CI，避免过早建设沙箱 |
| 一致性 | 权限、菜单、契约可在构建期强制校验 |
| 复杂度 | 动态加载涉及依赖隔离、版本地狱、迁移冲突，过早引入拖垮内核 |
| 演进 | SDK 与 Manifest 稳定后，可在不改业务插件声明的前提下替换加载器 |

## 后果

### 正面

- 架构清晰，团队可快速交付参考插件与能力插件  
- CI 可对 Manifest、依赖 DAG、权限冲突做强门禁  
- 与模块化单体战略一致  

### 负面 / 风险

- 新插件需改平台发版（可接受为第一方模型成本）  
- 「停用」不等于进程内物理卸载代码体积  
- 未来若强需求独立发版，需新增加载器（见升级条件）  

### 不做什么

- 不宣称支持不可信第三方插件  
- 不在 Phase 0–4 实现 Module Federation 热插拔  
- 不实现插件私有 migration 自动编排器  

## 升级触发条件（进入运行时模型前必须全部评估）

1. 明确需要**不改平台镜像**即可上线/回滚插件版本  
2. 具备独立插件发版与兼容性测试流水线  
3. 完成加载器 ADR（隔离级别、签名、回滚、migration 策略）  
4. 安全评估通过（至少：权限仍强制、无任意代码执行面扩大不可控）  

届时修订本 ADR 状态为「被取代」，并新增 ADR-00x。

## 备选方案（未采纳）

| 方案 | 未采纳原因 |
|------|------------|
| 纯运行时热插拔 | 成本高、与当前团队规模与工期不匹配 |
| 完整混合（一期就做运行时集成插件） | 双轨维护 Manifest 加载路径，易分裂 |
| 微前端多仓 | 增加发布与体验一致性成本；非插件系统必要条件 |
